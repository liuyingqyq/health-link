# 长时任务与后台保活

> 这篇文档只讲一件事：**为什么手机退到后台 3 秒后采集就断了，以及本项目怎么解决**。
> 所有约束都来自华为官方文档，凡是"官方没明说"的地方我都会标注出来。

---

## 1. 系统默认会做什么

官方明文：

* **应用退到后台超过 3 秒即被系统挂起**，冻结软硬件资源。
* **资源紧张时进程可能被直接回收**（不是"可能被限速"，是直接杀掉）。
* 后台默认运行时间窗口约 **10 分钟**（这是"能跑一会儿"的窗口，不是保活）。

对数据采集的直接影响：**不申请长时任务，退后台就等于停止采集**，
而且因为进程被冻结，连"断线重连"都不会发生。

---

## 2. 长时任务（Continuous Task）

### 2.1 三条硬要求（缺一不可）

| # | 要求 | 本项目落地位置 |
| --- | --- | --- |
| 1 | `module.json5` 声明 `requestPermissions: [ohos.permission.KEEP_BACKGROUND_RUNNING]` | `entry/src/main/module.json5` |
| 2 | `module.json5` 的 `abilities[].backgroundModes` 声明配置项字符串 | 同上（`["bluetoothInteraction", "dataTransfer"]`） |
| 3 | 在 **UIAbility** 里调用 `backgroundTaskManager.startBackgroundRunning(...)` | `service/ContinuousTaskManager.ets` + `EntryAbility` |

> **注意**：`backgroundModes` 里填的是**配置项字符串**（小驼峰），
> 而 API 侧用的是 `backgroundTaskManager.BackgroundMode` 枚举 —— 这是两套东西，
> 别把枚举名写进 `module.json5`。

### 2.2 权限等级：普通应用可以申请

`ohos.permission.KEEP_BACKGROUND_RUNNING` 的等级是 **normal / system_grant**，
**普通应用可直接申请，不需要 system_basic**。

需要 system_basic（受限）的是另外两个，只在特定场景叠加，本项目**不使用**：

* `ohos.permission.KEEP_BACKGROUND_RUNNING_SYSTEM`（API 20，`taskKeeping` 场景）
* `ohos.permission.KEEP_BACKGROUND_RUNNING_SPECIAL_SCENARIO`（API 24）

### 2.3 ⚠️ Stage 模型下只有 UIAbility 能申请

官方明文：「Stage 模型中，长时任务仅支持 UIAbility 申请；FA 模型中，长时任务仅支持 ServiceAbility 申请。」

这意味着：

* **`ContinuousTaskExtensionAbility` 这个类不存在**（官方文档与 SDK 声明中均查无此物，
  `module.json5` 的 `extensionAbilities.type` 合法值里也没有 `continuousTask`）。
  你原始需求里的示例 4 无法实现，本项目已移除。
* 采集服务必须拿到 `UIAbility.context`。本项目在 `EntryAbility.onCreate` →
  `onWindowStageCreate` 里把 `this.context` 注入单例 `CollectionService`。

### 2.4 ⚠️ DATA_TRANSFER：10 分钟不更新进度就会被取消

官方对 `DATA_TRANSFER` 的原话：

> 在数据传输过程中，应用需要更新进度。**如果超过 10 分钟未更新进度，
> DATA_TRANSFER 类型的长时任务将被取消。** 进度更新的通知类型**必须为实况窗**。

你原始需求里的 `startContinuousTask()` **没有任何进度更新**，按字面实现会在 10 分钟后失效。

**本项目的处理**：

* 主模式用 **`BLUETOOTH_INTERACTION`** —— 健康数据来自蓝牙穿戴设备，
  这是场景最匹配的模式，而且**没有 10 分钟硬性续期要求**。
* 同时叠加 `DATA_TRANSFER`（因为确实在持续上传），并对它做续期：
  每 **5 分钟**（< 10 分钟硬限）刷新一次常驻通知的进度文案。
* 采集循环**每轮**也会调用 `updateProgress()`，把"已采集 N 项 + 最近一项的值"写进通知，
  这样续期与实际业务活动绑定，不是空转刷通知。

```typescript
// service/ContinuousTaskManager.ets
const PROGRESS_UPDATE_MS = 5 * 60 * 1000;   // 官方硬限 10 分钟，取 5 分钟留余量
await backgroundTaskManager.startBackgroundRunning(
  this.context,
  ['bluetoothInteraction', 'dataTransfer'],   // API 12+ 的字符串数组重载，一次申请两种
  agent
);
```

### 2.5 ⚠️ 通知栏常驻：用户删掉通知 = 任务被停止

官方明文：「应用申请长时任务成功后，系统会在通知栏显示与长时任务相关联的消息，
**用户删除通知栏消息时，系统会自动停止长时任务**。」

所以"通知栏常驻不可隐藏"不只是体验问题，而是**功能存亡问题**。
本项目的通知：

* `isOngoing: true` + `isUnremovable: true` + `tapDismissed: false`
* 文案明确写：**「请勿删除本通知，删除后系统会停止后台采集」**
* 点击通知通过 `WantAgent` 拉回应用主界面
* 发布失败（用户关了通知权限）**不阻断采集** —— 只记日志，因为长时任务本身已经申请成功

### 2.6 ⚠️ 业务真实性检测（本项目无法验证的风险）

官方明文：「系统会检测业务真实性，若未实际执行对应业务，可能取消长时任务并挂起应用。」

本应用做的是"周期性读取健康数据并上传"。**它是否会被判定为真实的
`bluetoothInteraction` / `dataTransfer` 业务，本项目没有真机，无法验证。**

如果真机上出现"长时任务被反复取消"，可尝试的调整（按优先级）：

1. 确认手机上确实连了蓝牙穿戴设备并在同步数据（这是 `bluetoothInteraction` 的业务前提）
2. 缩短采集周期（默认 60 秒，可降到 30 秒），提高业务活跃度
3. 只保留 `['bluetoothInteraction']`，去掉 `dataTransfer`
   （代价：批量补传时可能被系统打断，但重连后会继续）

调整位置：`service/CollectionService.ets` 的 `start()` 方法里那行 `this.background.start([...])`。

### 2.7 错误码对照（本项目已内置中文提示）

| 错误码 | 含义 | 项目内的提示 |
| --- | --- | --- |
| 201 | 权限被拒 | 提示检查 `KEEP_BACKGROUND_RUNNING` 权限与 `backgroundModes` 声明 |
| 202 | 非系统应用 | 提示该操作不允许 |
| 401 | 参数错误 | 提示 context 必须是 UIAbility 的 |
| 9800001–9800007 | 长时任务相关错误 | 提示数量超限 / 类型不支持 / 已被取消 |

对应代码：`ContinuousTaskManager.explainFailure()`。

## 3. 应用预加载

### 3.1 官方事实

* 机制**从 API 20 起**，**仅 2in1 设备**，**仅 entry 模块**的 AbilityStage / UIAbility。
* 是否预加载、什么时机，**由系统按用户习惯与资源自行决定，开发者无法干预**。
* 三阶段：`processCreated` / `abilityStageCreated` / `windowStageCreated`，
  通过在 `app.json5` 里声明 `appPreloadPhase` 参与。
* `application.getAppPreloadType()` **起始 API 22**。

### 3.2 ⚠️ 两个常见错误说法

| 错误说法 | 正确说法 |
| --- | --- |
| 「初始化至 `WindowStage.onCreate`」 | **不存在 `WindowStage.onCreate`**。正确是 **`UIAbility.onWindowStageCreate(windowStage)`** |
| 「`getAppPreloadType()` 从 API 12 就有」 | **API 22 起**才有。低版本调用会抛错，必须 `try/catch` |

### 3.3 调用时机很关键

官方原文：「只有在进程**首次执行 `AbilityStage.onCreate` 完成之前**调用该接口，
才可以返回真实的预加载类型。AbilityStage 创建完成后，应用的预加载数据将被清除，
调用该接口将返回 `UNSPECIFIED`。」

→ 必须在 `AbilityStage.onCreate()` 的**第一件事**就调用。

### 3.4 本项目怎么用

```typescript
// entryability/MyAbilityStage.ets
onCreate(): void {
  // ★ 必须在这里调用，晚一点就只能拿到 UNSPECIFIED
  this.preloadInfo = detectPreloadType();
  ...
  // 预加载路径下提前把偏好存储准备好，省掉用户点开后的等待
  AppPrefs.init(this.context).then(...);
}
```

`detectPreloadType()` 用 `try/catch` 包住，低版本设备（API < 22）返回
"当前系统不支持预加载查询"，**不当作错误**，也不影响应用启动。

### 3.5 ⚠️ 配置陷阱：`AbilityStage` 必须在 module.json5 里声明

很多示例漏了这一项，导致 `AbilityStage.onCreate` 根本不执行：

```json5
// entry/src/main/module.json5
{
  "module": {
    "name": "entry",
    "srcEntry": "./ets/entryability/MyAbilityStage.ets",   // ← 就是这一行
    "mainElement": "EntryAbility",
    ...
  }
}
```

你原始需求的 `module.json5` 片段里没有这一项，本项目已补上。

## 4. 完整的保活链路（本项目实际实现）

```
用户在 App 里点「开始采集」
        │
        ├─▶ 1. 运行时权限申请（INTERNET / GET_NETWORK_INFO / KEEP_BACKGROUND_RUNNING）
        │
        ├─▶ 2. healthStore.init(context)         ← 必须是 UIAbility 的 context
        │
        ├─▶ 3. healthStore.requestAuthorizations()  ← 用户授权健康数据读取
        │
        ├─▶ 4. backgroundTaskManager.startBackgroundRunning(
        │          context, ['bluetoothInteraction','dataTransfer'], agent)
        │      └─▶ 发常驻通知（isOngoing + isUnremovable）
        │      └─▶ 启动 5 分钟进度续期定时器（防 DATA_TRANSFER 被取消）
        │
        ├─▶ 5. 连接电脑（WebSocket），首条发 hello（带 lastSeq）
        │      └─▶ 收到 hello_ack → 按需补传 batch → 按电脑下发周期调整节奏
        │
        └─▶ 6. 采集循环（默认 60 秒一轮，官方建议间隔 ≥ 1 分钟）
               · 依次读 heart_rate / resting_heart_rate / hrv / spo2 / stress
               · 单独读 sleepRecord（健康记录，走另一条 API 路径）
               · 每条样本立刻发送（seq 单调递增，本地持久化）
               · 发不出去就进离线队列（上限 2000 条，超限丢最旧并计数）
               · 每轮刷新通知进度（同时完成长时任务续期）
```

退到后台时：`onBackground()` 只记日志，**不停止采集**——停止采集就等于放弃长时任务的意义。

## 5. 手机端自己也要"长加载"

除了系统级长时任务，手机端内部还有两层韧性：

| 层 | 机制 | 位置 |
| --- | --- | --- |
| 连接层 | 断线后 1s/2s/4s/8s/16s/30s 退避重连，上限 30s，**永不放弃** | `transport/LanWsTransport.ets` |
| 数据层 | 未连上时信封进离线队列（上限 2000），连上后按序补发 | 同上 |
| 补传层 | 重连时带 `lastSeq`，电脑算出缺口后发 `batch` 补传 | `service/CollectionService.ets` |
| 心跳层 | 30 秒应用层 ping/pong + WebSocket 协议层心跳 | 传输层 + 电脑端 `ws.js` |

关于"补传"的**诚实说明**：手机端只在内存里保留**最近一轮**采集样本，
所以补传覆盖的是短暂闪断；断线时间较长时产生的缺口会通过 `gap` 消息
**如实告知电脑端**，不假装补全。详见 `docs/README.md` 的「已知限制」。
